# 费用核销、批量核销与反核销统一设计

## 1. 背景与目标

当前费用记录在 PC 端与小程序端存在以下不一致：

- 小程序将费用核销权限映射为 `finance:expense:edit`，导致拥有编辑权限但不应拥有核销权限的店长、主管仍能看到核销按钮。
- 后端单笔核销与批量核销也复用 `finance:expense:edit`，权限边界不清晰。
- PC 端已有选择借支单和批量核销入口，小程序仍调用不选择借支单的单笔核销接口。
- 两端均缺少反核销能力。
- 现有批量核销可能生成补款或节余借支记录，但没有完整的核销批次台账，无法安全、可审计地逆向恢复。

本设计的目标是让 PC 端、小程序端共享同一套权限、接口和账务规则，并提供可审计、可回滚且受核算周期约束的反核销能力。

## 2. 已确认业务决策

1. 已结转或已锁定核算周期内的费用禁止反核销。
2. 禁止规则必须由后端执行，前端按钮状态只用于改善交互。
3. 单笔核销视为只有一笔费用的批量核销，统一使用同一业务服务。
4. 反核销按核销批次整体执行，不支持拆分撤销批次中的单笔费用。
5. 反核销必须填写原因，并完整记录操作人、时间和数据变化。
6. 历史核销关系无法可靠还原时，默认禁止自动反核销。

## 3. 方案选择

采用“独立核销权限 + 核销批次台账”方案。

不采用仅补前端按钮的方式，因为前端鉴权可被绕过；不采用仅依赖现有 `advanceId` 反推关系的方式，因为多费用、多借支以及补款、节余场景无法无歧义恢复。

## 4. 权限模型

新增独立权限：

| 权限码 | 用途 |
| --- | --- |
| `finance:expense:verify` | 单笔核销和批量核销 |
| `finance:expense:unverify` | 反核销 |
| `finance:expense:edit` | 修改未核销费用，不再代表核销 |
| `finance:advance:list` | 查询核销时可选择的借支单 |

建议默认授权：

- 店长、主管：不授予 `verify`、`unverify`。
- 财务人员：授予 `verify`。
- 财务主管或管理员：授予 `verify`、`unverify`。
- 超级管理员继续兼容 `*:*:*`。

数据库菜单中现有“费用核销”按钮不得继续使用 `finance:expense:edit`，应迁移为 `finance:expense:verify`，并新增“费用反核销”按钮权限。

PC 和小程序使用权限码控制按钮显示；后端控制器必须使用相同权限码保护接口。角色名称不写死在客户端或业务服务中。

## 5. 核心数据模型

### 5.1 核销批次表 `fin_expense_verify_batch`

建议字段：

- `batch_id`：主键。
- `batch_no`：业务批次号，唯一。
- `request_id`：客户端幂等号，在租户范围内唯一。
- `tenant_id`：租户标识。
- `dept_id`：门店或部门标识。
- `period_id`：核销发生时所属核算周期；若批次允许涉及多个周期，则改由明细保存并禁止跨门店。
- `total_expense_amount`：费用合计。
- `total_advance_amount`：原始借支合计。
- `difference_amount`：费用与借支差额。
- `status`：`VERIFIED` 或 `REVERSED`。
- `verify_by`、`verify_time`：核销人和核销时间。
- `reverse_by`、`reverse_time`、`reverse_reason`：反核销信息。
- `version`：乐观锁版本。
- 通用创建、更新和逻辑删除字段。

### 5.2 费用核销明细表 `fin_expense_verify_detail`

- `detail_id`
- `batch_id`
- `expense_id`
- `expense_amount`
- `original_status`
- `original_advance_id`
- `period_id`

`batch_id + expense_id` 建立唯一约束，防止同一费用重复加入同一批次。

### 5.3 借支核销明细表 `fin_advance_verify_detail`

- `detail_id`
- `batch_id`
- `advance_id`
- `advance_amount`
- `original_status`
- `period_id`
- `relation_type`：`SOURCE`、`SUPPLEMENT` 或 `SURPLUS`。
- `generated_flag`：是否由本次核销生成。

批次、费用明细、借支明细均保留租户和门店归属，查询和更新必须附带租户、数据权限条件。

### 5.4 兼容字段

现有费用表中的 `advance_id` 暂时保留，用于兼容旧查询和展示，但不再作为反核销的唯一依据。新增数据以核销明细表为权威关系来源。

## 6. 统一核销流程

### 6.1 API

统一接口：

```text
PUT /finance/expense/batchVerify
Permission: finance:expense:verify
```

请求示例：

```json
{
  "expenseIds": [101, 102],
  "advanceIds": [201, 202],
  "requestId": "6cfdeec3-6485-46ef-bb75-5d6b12ab02b2"
}
```

单笔核销也调用该接口，`expenseIds` 仅包含一个 ID。原 `/verify/{expenseId}` 在过渡期可以保留，但必须委托统一核销服务，并最终下线。

### 6.2 后端校验

在单一数据库事务中依次执行：

1. 校验请求幂等号、费用 ID 非空且无重复。
2. 按当前租户和数据权限查询全部费用；查回数量必须与请求数量一致。
3. 校验所有费用属于同一可操作门店且均为未核销。
4. 按当前租户和门店查询借支单；查回数量必须与请求数量一致。
5. 校验借支单均未核销、未被其他并发核销占用。
6. 校验费用和借支涉及的核算周期均处于可编辑状态。
7. 使用条件更新或行锁防止并发重复核销。
8. 创建核销批次和明细快照。
9. 更新费用、原始借支状态。
10. 根据差额生成补款或节余借支，并以 `SUPPLEMENT` 或 `SURPLUS` 明细关联到批次。
11. 写入审计日志并提交事务。

任一步骤失败必须整体回滚，不返回部分成功。

### 6.3 金额规则

- 费用合计等于借支合计：核销费用和所选借支，不生成差额记录。
- 费用合计大于借支合计：按现有业务规则生成补款记录，并标记为批次生成记录。
- 费用合计小于借支合计：按现有业务规则生成节余记录，并标记为批次生成记录。
- 未选择借支单时允许仅核销费用，但批次仍必须生成，以支持审计和反核销。

金额计算统一使用 `BigDecimal`，比较前明确精度和舍入规则，不使用浮点数。

## 7. 反核销流程

### 7.1 API

```text
PUT /finance/expense/unverify/{batchId}
Permission: finance:expense:unverify
```

请求示例：

```json
{
  "reason": "借支单选择错误",
  "requestId": "734bf57a-6a15-47ff-bde0-b9936657e6ac"
}
```

`reason` 必填并限制合理长度；`requestId` 用于避免重复提交。

### 7.2 禁止条件

以下任一条件成立时拒绝反核销：

- 用户缺少 `finance:expense:unverify`。
- 批次不存在、不属于当前租户或超出用户门店数据权限。
- 批次已反核销。
- 任一相关费用、原始借支或核销生成记录所属周期已锁定或已结转。
- 核销生成的补款或节余记录已被后续核销、结算或其他业务引用。
- 费用或借支当前状态与批次记录不一致，存在后续修改或数据异常。
- 历史数据被标记为无法可靠还原的 `LEGACY` 批次。

周期锁定和结转判断必须调用现有核算周期领域服务，不在控制器或前端复制规则。

### 7.3 原子恢复

在单一事务中执行：

1. 锁定批次及相关费用、借支记录。
2. 再次执行权限、归属、状态、周期和后续引用校验。
3. 将费用恢复为核销前状态，清空当前核销人、核销时间和兼容关联字段。
4. 将原始借支恢复为核销前状态。
5. 将本批次生成的补款或节余记录标记作废或逻辑删除，不物理删除。
6. 将批次状态更新为 `REVERSED`，记录反核销人、时间、原因。
7. 写入包含前后快照的审计日志。

任何一步失败全部回滚。反核销不删除批次及明细，以保留完整审计链。

## 8. PC 端设计

- 将现有“核销”和“批量核销”按钮权限替换为 `finance:expense:verify`。
- 单笔和批量入口都打开统一核销弹窗，展示已选费用、可用借支、费用合计、借支合计、差额及差额处理结果。
- 已核销记录在拥有 `finance:expense:unverify` 时显示“反核销”。
- 反核销前展示批次内费用、借支、补款或节余记录，并要求填写原因后二次确认。
- 周期已锁定或已结转时禁用反核销并显示明确原因。
- 提供核销批次详情查看入口，便于审计和问题排查。

## 9. 小程序设计

### 9.1 权限一致性

模块配置中将：

```text
verify: finance:expense:edit
```

替换为：

```text
verify: finance:expense:verify
unverify: finance:expense:unverify
```

无核销权限时，费用详情不显示核销按钮，列表不显示批量核销入口。前端缓存权限只能用于展示，接口返回的无权限结果必须正常提示。

### 9.2 批量核销交互

1. 费用列表增加“批量核销”入口。
2. 进入多选模式后，仅未核销费用可选。
3. 固定底部栏展示已选笔数和费用合计。
4. 下一步选择当前门店可用的未核销借支单。
5. 确认页展示费用合计、借支合计、差额和差额处理说明。
6. 提交时生成 `requestId`，调用统一批量核销接口。
7. 成功后刷新列表、统计和详情；失败时保留选择并显示后端业务错误。

详情页“核销”进入同一流程，只是预选当前费用。

### 9.3 反核销交互

- 已核销费用详情展示所属核销批次。
- 有反核销权限且后端判定可操作时显示“反核销”。
- 用户必须填写原因并二次确认。
- 周期锁定、已结转或存在后续引用时，不允许提交并显示具体原因。

## 10. 操作能力返回

为避免 PC 和小程序各自复制复杂规则，费用详情或批次详情接口建议返回服务端计算的操作能力：

```json
{
  "canVerify": false,
  "canUnverify": false,
  "operationDisabledReason": "所属核算周期已锁定"
}
```

权限码仍由客户端用于快速隐藏入口；`canVerify`、`canUnverify` 用于反映数据状态、周期状态及后续引用约束。提交接口必须重新校验，不能信任查询时返回的能力值。

## 11. 历史数据迁移

1. 根据现有费用、借支及关联字段识别可无歧义还原的核销关系，为其生成历史迁移批次。
2. 无法明确判断关系的已核销记录生成或标记为 `LEGACY` 批次。
3. `LEGACY` 批次默认不可自动反核销，需财务管理员人工核对并补全关系后才可操作。
4. 迁移脚本必须支持预演、统计、重复执行保护和异常清单导出。
5. 上线前对费用总额、借支总额、已核销金额和未核销余额进行迁移前后对账。

## 12. 并发、幂等与审计

- 核销和反核销均要求客户端幂等号，并建立唯一约束。
- 状态更新使用条件更新、行锁或乐观锁，确保两个请求不能同时处理同一费用或批次。
- 审计日志记录操作类型、租户、门店、批次号、操作人、原因、请求号以及关键数据前后快照。
- 不允许物理删除核销批次、明细和核销生成的差额记录。
- 错误响应区分无权限、周期锁定、状态冲突、后续引用和数据异常，方便两端准确提示。

## 13. 测试与验收

### 13.1 权限

- 店长、主管在 PC 和小程序均看不到核销、批量核销和反核销入口。
- 店长、主管绕过前端直接调用接口时返回无权限。
- 编辑、核销、反核销三个权限可独立授权。

### 13.2 核销

- 单笔和批量核销均能选择借支单。
- 等额、补款、节余、无借支四种金额场景结果正确。
- 混入已核销费用、不可用借支或越权门店数据时整批失败。
- 重复提交同一 `requestId` 不产生重复批次或差额记录。
- 并发核销同一费用时最多一个请求成功。

### 13.3 反核销

- 正常批次可完整恢复费用、原始借支及核销生成记录。
- 已锁定或已结转周期在 PC、小程序及直接接口调用下均被禁止。
- 存在后续引用时禁止反核销。
- 已反核销批次不可重复反核销。
- 事务任一步失败时数据保持核销前状态，不出现部分恢复。
- 反核销原因和前后快照可在审计日志中查询。

### 13.4 回归

- 已核销费用仍不可编辑、不可删除。
- 费用统计、成本核算、现金流、核算周期检查等报表结果与核销状态同步。
- PC 与小程序在相同账号、相同记录下展示相同的可操作能力。

## 14. 上线顺序与回滚

建议按以下顺序发布：

1. 数据库表、索引、权限菜单和历史迁移脚本。
2. 后端批次化核销、反核销及兼容旧接口。
3. PC 端权限与交互。
4. 小程序权限、借支选择和批量核销。
5. 历史数据迁移、全量对账和角色授权复核。
6. 观察稳定后下线旧单笔核销接口。

发布期间后端应先兼容旧客户端。若应用版本需要回滚，批次表和明细表保留，不回滚或删除已经产生的审计数据；旧接口仍委托统一服务，避免恢复到无台账的核销路径。

## 15. 实施边界

本次范围包含费用核销权限拆分、费用单笔/批量核销统一、借支选择、反核销、批次审计以及 PC/小程序一致性。

不在本次范围内：通用财务凭证冲销体系、跨门店核销、锁定周期自动解锁、对历史 `LEGACY` 数据进行无依据的自动恢复。
