# 统一业务模型与配置生命周期设计

## 1. 目标与范围

本设计是峻松云低代码与智能工作流长期演进的阶段 0 设计，目标是建立稳定的统一业务模型和安全的配置生命周期，为后续模板、简易画布和 AI 生成打基础。

本阶段只处理：

- 业务对象、字段、页面、流程节点、分支规则、动作、后置动作、定时器的统一聚合关系；
- 草稿、校验、发布、版本、回滚、历史和差异读取；
- 发布影响分析；
- 数量、金额、日期、日期时间字段的统一元数据约束；
- 租户、部门、权限、财务和历史实例的版本边界。

本阶段不处理：

- AI 对话或 AI Agent；
- 模板市场和业务配置向导；
- 新增复杂 BPMN 节点；
- Flowable 升级或替换；
- 全量前端重构；
- 任意脚本、SQL 或未审计动作节点。

## 2. 现状与问题

### 2.1 已有能力

- `LcBizConfigDTO` 已聚合 `LcBizObject`、字段、页面 Schema、节点处理人、分支规则、动作、后置动作和定时器。
- `LcMetadataSchemaValidator` 已提供字段、页面、处理人和分支规则的发布前静态校验。
- `LcMetadataServiceImpl.saveBizConfig` 已提供事务性保存入口，但子表使用物理删除后批量插入。
- `LcConfigVersionServiceImpl.publish` 已能生成 JSON 快照、更新 `configStatus` 和 `publishedVersion`。
- `LcConfigVersionServiceImpl.rollback` 已能将快照恢复为草稿，但复用了保存逻辑，且没有在回滚前生成影响报告。
- 前端已有低代码配置、表单设计、运行时页面、流程设计和版本入口。

### 2.2 本阶段必须修正的边界

1. 配置模型缺少明确的模型版本、字段类型契约和时间/精度元数据。
2. 保存、发布、回滚的状态转换没有形成统一状态机。
3. `MAX(version_no)+1` 在并发发布下存在版本号冲突风险。
4. 回滚后必须重新发布，但当前缺少明确的回滚影响说明和重新校验边界。
5. 已运行实例必须绑定启动时版本，不能因为后续发布而隐式改变历史实例。
6. 发布影响分析目前没有统一输出结构，前端无法向用户解释“发布改变了什么”。

## 3. 统一业务模型

### 3.1 模型层次

```text
BusinessApp / BizConfig
├── BizObject                 业务对象、存储和流程绑定
├── Fields[]                  字段与精度、时区、组件元数据
├── PageSchemas[]             LIST / FORM / DETAIL / TASK 页面布局
├── Workflow                  流程定义引用与节点配置
│   ├── NodeAssignees[]       节点处理人
│   ├── BranchRules[]         分支规则
│   └── NodeTimers[]          节点定时器
├── Actions[]                 用户动作与状态转换
├── PostActions[]             流程事件后的受控动作
└── Lifecycle                 草稿、发布、回滚、版本和审计
```

### 3.2 配置聚合体契约

保留 `LcBizConfigDTO` 作为 Java 内部聚合体，但增加以下顶层契约字段：

| 字段 | 类型 | 规则 |
|---|---|---|
| `modelVersion` | String | 统一业务模型版本，例如 `1.0`；缺失时只允许兼容读取，不允许新发布 |
| `schemaVersion` | Integer | 页面和字段契约版本，随结构性变更递增 |
| `configStatus` | Enum | `DRAFT`、`PUBLISHED`、`ROLLBACK_DRAFT` |
| `publishedVersion` | Integer | 当前生效快照版本；草稿变更不得改写此值 |
| `sourceVersion` | Integer | 草稿基于的发布版本，用于并发编辑检测 |
| `timezone` | String | 固定 `Asia/Shanghai`，不允许业务配置覆盖 |
| `publishRemark` | String | 发布或回滚原因，必须进入审计 |

所有子对象必须带 `bizCode`，保存入口统一由服务端补齐并校验，客户端传入的跨业务对象引用一律拒绝。

### 3.3 字段类型契约

| 业务类型 | 允许值 | 存储/计算 | 展示 |
|---|---|---|---|
| `quantity` | 正数、负数、零 | `BigDecimal`，3 位小数 | `0.000` |
| `amount` | 正数、负数、零 | `BigDecimal`，2 位小数，`HALF_UP` | `0.00` |
| `date` | 日期 | `Asia/Shanghai` 业务日 | `YYYY-MM-DD` |
| `datetime` | 日期时间 | `Asia/Shanghai`，秒级 | `YYYY-MM-DD HH:mm:ss` |

空值必须与零值区分。低代码字段必须通过明确的 `valueType` 或等价字段元数据声明上述类型，禁止用普通字符串、JavaScript 浮点数或未声明的 `number` 承载业务数量和金额。

### 3.4 版本化快照

快照 JSON 必须包含：

- `modelVersion`、`schemaVersion`；
- 完整配置聚合体，而不是只保存发生变化的子表；
- 创建人、创建时间、租户和发布说明；
- 配置内容校验摘要 `contentHash`；
- 兼容迁移标识，便于未来模型升级。

快照是历史事实，不允许被后续保存覆盖。回滚的语义是“将指定快照复制为新的草稿”，不是修改历史快照。

## 4. 配置生命周期

```text
不存在
  ↓ 新建
DRAFT ──保存──→ DRAFT
  │              │
  │ 发布前校验    │ 基于已发布版本编辑
  ↓              ↓
PUBLISHED ←──发布── DRAFT
  │
  └──选择历史版本──→ ROLLBACK_DRAFT ──校验/保存──→ DRAFT
```

规则：

- 保存只改变草稿和子配置，不改变当前已发布快照。
- 发布必须在同一事务中完成：读取草稿、完整校验、生成影响报告、创建新快照、更新当前版本和刷新运行时缓存。
- 发布失败时不得留下部分子表、半个快照或错误的当前版本。
- 回滚只产生草稿，必须重新执行校验和发布；回滚动作必须记录来源版本和操作者。
- 发布时必须检查 `sourceVersion`，如果草稿不是基于当前发布版本，默认拒绝并要求重新读取合并。
- 历史流程实例绑定启动时的 `configVersion`；新发布只影响新实例。

## 5. 发布影响报告

发布和回滚预览统一返回：

```json
{
  "bizCode": "expense_apply",
  "sourceVersion": 3,
  "targetVersion": 4,
  "severity": "WARNING",
  "blocking": false,
  "items": [
    {
      "kind": "FIELD",
      "key": "amount",
      "change": "PRECISION_CHANGED",
      "severity": "BLOCKING",
      "message": "金额字段必须保留 2 位小数"
    }
  ],
  "affected": {
    "pages": ["FORM", "DETAIL"],
    "workflow": "expense_apply",
    "permissions": [],
    "menus": [],
    "runningInstances": 12
  }
}
```

影响级别：

- `BLOCKING`：模型不合法、字段类型不兼容、处理人缺失、权限越权、跨租户引用、并发版本冲突；禁止发布。
- `WARNING`：删除展示字段、改变页面布局、改变未启动流程的规则；需要用户确认。
- `INFO`：新增可选字段、增加说明、无运行影响的页面调整。

## 6. 数据与并发设计

### 6.1 保存策略

第一版保留现有“聚合保存 + 子表替换”模式，避免本阶段引入复杂增量编辑；但必须：

- 在事务内执行；
- 先完整校验，再删除和插入；
- 使用 `sourceVersion` 防止旧草稿覆盖新发布配置；
- 所有删除和插入都带租户和 `bizCode` 范围；
- 保存失败回滚全部子表变更；
- 发布快照在保存完成后读取，保证快照与当前草稿一致。

### 6.2 发布并发

数据库为 `biz_code + version_no` 增加唯一约束；发布版本号不再只依赖无锁的 `MAX` 查询。发布事务必须锁定业务对象或使用条件更新，冲突时返回可读错误，不自动覆盖。

### 6.3 历史实例

`lc_biz_instance` 或等价流程实例业务记录需要保存：

- `bizCode`；
- `configVersion`；
- 启动时的 `modelVersion`；
- 业务租户和部门范围。

历史详情读取必须按实例绑定版本解释页面和字段，不直接使用当前最新配置。

## 7. API 设计

保留现有兼容接口，增加以下能力：

| API | 用途 |
|---|---|
| `GET /workflow/lowcode/meta/config/{bizCode}` | 读取聚合配置及生命周期信息 |
| `POST /workflow/lowcode/meta/config/validate` | 只校验，不写库，返回结构化报告 |
| `POST /workflow/lowcode/meta/config/impact` | 计算发布或回滚影响，不发布 |
| `POST /workflow/lowcode/meta/config` | 保存草稿，携带 `sourceVersion` |
| `POST /workflow/lowcode/meta/config/publish/{bizCode}` | 携带发布说明和预览确认令牌后发布 |
| `GET /workflow/lowcode/meta/config/history/{bizCode}` | 查询历史快照摘要 |
| `GET /workflow/lowcode/meta/config/snapshot/{bizCode}/{versionNo}` | 查看完整快照 |
| `POST /workflow/lowcode/meta/config/rollback/{bizCode}` | 复制快照为草稿，不直接生效 |

发布确认令牌必须由同一份影响报告生成，内容包括 `bizCode`、`sourceVersion`、内容摘要和操作者；报告过期或配置内容变化时必须重新预览。

## 8. 前端设计

阶段 0 只做治理型页面，不做新的业务向导：

- 配置状态条：草稿版本、当前发布版本、最后发布人和北京时间。
- 校验报告：按阻断、警告、提示分组，定位到对象、字段、页面或节点。
- 影响预览：展示表单、流程、菜单、权限和运行实例影响。
- 版本历史：查看摘要、完整快照、差异和回滚入口。
- 回滚确认：明确“回滚生成草稿，仍需重新发布”。

前端必须复用现有请求、权限、字典、金额和日期工具；金额展示使用两位小数，数量使用三位小数，时间使用 `Asia/Shanghai` 和 `YYYY-MM-DD HH:mm:ss`。

## 9. 测试与验收

### 后端

- DTO 聚合读取字段完整且同一 `bizCode`；
- 字段、页面、节点、分支引用校验；
- 数量正负值和 3 位小数；
- 金额正负值、2 位小数和 `HALF_UP`；
- 日期格式、北京时间和禁止 `T` 展示；
- 保存事务失败时子表不残留；
- 发布版本并发冲突；
- 发布快照不可被覆盖；
- 回滚只生成草稿；
- 历史实例按绑定版本读取；
- 租户、部门和权限越权被拒绝。

### 前端

- 配置状态与版本显示正确；
- 阻断报告不能点击发布；
- 警告必须二次确认；
- 回滚页面明确重新发布语义；
- 日期不出现 `T`；
- 金额和数量输入、导入、展示精度一致。

### 阶段退出验收

使用费用报销业务对象完成：

```text
读取配置 → 修改字段/页面/处理人 → 静态校验
→ 查看影响报告 → 保存草稿 → 发布 v1
→ 再次修改 → 发布 v2 → 查看差异
→ 回滚 v1 为草稿 → 校验 → 重新发布 v3
→ 验证历史实例仍按启动版本读取
```

只有上述链路全部通过，阶段 0 才能进入 G4 退出确认。
