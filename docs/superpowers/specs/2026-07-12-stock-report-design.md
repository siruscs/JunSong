# 库存报表设计规格

## 1. 目标

分两期完成库存报表：第一期开放可追溯、可对账、严格隔离租户和授权门店的经营库存报表；第二期在稳定库存事实层上增加移动加权平均成本、库存金额、销售成本和毛利核对。

库存报表不得直接依赖 `fin_product.stock_num` 作为事实来源。库存事实来源限定为：

- `fin_stock_ledger`：不可变库存变动流水；冲销通过反向流水表达。
- `fin_stock_position`：当前库存结存。
- `fin_stock_snapshot`：按自然日固化的期初、入库、出库、期末及金额快照。

## 2. 当前状态与阻断

现有系统已经具备采购入库、销售出库、采购冲销、销售冲销、当前结存和每日快照底座，但库存报表仍返回“暂不开放”，PC 页面也是暂停说明页。

开放前必须解决以下阻断：

1. 三张库存表虽然已有补充 `tenant_id` 的迁移脚本，但 Java 实体、Mapper 参数、SQL 条件、行锁、幂等查询、唯一键和快照任务尚未形成完整的 `tenant_id + dept_id` 隔离链路。
2. 当前库存行主要按 `dept_id + product_id` 锁定，不能证明不同租户之间绝对隔离。
3. 存量数据可能存在结存无流水、流水累计与结存不一致、快照缺失或快照与结存不一致。
4. 销售出库流水尚未固化可靠成本，不能直接提供财务库存金额和销售成本。
5. 系统没有完整的盘点、调拨、采购退货、销售退货业务入口，第一期不能虚构这些变动类型。

## 3. 方案选择

采用“先加固库存底座，再开放报表”的方案。

不采用直接查询现有表并立即开放的方式，因为这会放大租户串数和历史口径不一致风险；不新建独立报表宽表，因为当前规模下会形成第二套库存事实来源和额外同步复杂度。

## 4. 第一期范围：经营库存报表

### 4.1 查询条件

- 授权门店：支持单门店和多门店，服务端将请求门店与当前用户授权部门集合取交集；交集为空时失败关闭。
- 日期区间：按自然日闭区间查询，时区使用应用统一时区。
- 商品：商品编码或名称模糊查询。
- 库存状态：正常、低库存、零库存、负库存、滞销、快照异常。
- 分页：商品明细必须服务端分页；汇总卡片基于完整授权结果，不基于当前页。

### 4.2 汇总指标

- 期初库存数量。
- 区间采购净入库数量。
- 区间销售净出库数量。
- 区间其他调整净数量，仅在以后出现真实、受控的调整入口后启用；第一期恒为零且前端不展示。
- 期末库存数量。
- 负库存商品数。
- 低库存商品数。
- 滞销商品数。
- 快照或流水对账异常商品数。

数量恒等式：

`期初数量 + 采购净入库数量 - 销售净出库数量 + 其他调整净数量 = 期末数量`

采购冲销计入采购净入库的负向变动，销售冲销计入销售净出库的负向变动。汇总和明细必须使用同一套 SQL 口径。

实物库存数量必须包含赠品：

- 进货单按每个商品的全部明细数量入库，不论 `is_gift` 是否为 `1`。赠品不计采购金额，但其 `quantity` 必须计入采购入库数量；同一商品普通明细与赠品明细合并为该商品的目标入库量。
- 销售单按 `sale_quantity + gift_quantity` 出库。赠品不计销售收入，但必须计入销售出库数量。
- 修改单据时按新的含赠品合计数量与该来源已记录净额做差额流水；删除或冲销时按原含赠品合计数量反向恢复。
- 报表的采购净入库和销售净出库直接汇总可信库存流水，不得再次从业务单据拼算，从而避免赠品重复计算或遗漏。

### 4.3 商品明细

每行至少包含：租户、门店、商品 ID、商品编码、商品名称、单位、最低库存、期初数量、采购净入库、销售净出库、期末数量、最近入库时间、最近出库时间、无出库天数、库存状态、对账状态。

跨门店查询默认按“门店 + 商品”展示，不把不同门店库存合并成一个不可追溯的数字。可额外提供商品汇总视图，但必须保留下钻到门店的能力。

### 4.4 流水下钻

从商品明细可查看区间库存流水，包含变动时间、变动类型、变动前数量、变动数量、变动后数量、来源类型、来源单号、操作人和备注。

来源单据跳转仅在用户同时拥有对应来源模块查询权限且来源记录仍存在时开放。删除或冲销的来源不能导致库存流水消失。

### 4.5 风险定义

- 负库存：期末数量 `< 0`。
- 低库存：期末数量 `> 0` 且 `<= min_stock`。
- 零库存：期末数量 `= 0`。
- 滞销：期末数量 `> 0` 且连续 30 天无有效销售出库；阈值使用系统配置并提供明确默认值 30。
- 快照异常：同日快照不满足期初、净变动、期末恒等式，或最新快照期末与对应重建结果不同。
- 流水异常：流水累计结果与 `fin_stock_position.quantity` 不一致，或存在结存但无任何有效流水。

异常只读展示，不允许报表接口自动修复库存。

### 4.6 导出

导出使用独立权限 `finance:report:stock:export`，复用查询条件和服务端授权部门集合。导出记录操作日志，不允许通过传入任意 `deptIds` 绕过数据范围。

## 5. 第一期底座加固

### 5.1 数据模型

三张库存表统一包含非空 `tenant_id`。关键唯一键至少调整为：

- `fin_stock_position`：`tenant_id + dept_id + product_id`。
- `fin_stock_snapshot`：`tenant_id + snapshot_date + dept_id + product_id`。

流水表增加覆盖报表查询的组合索引，优先顺序为 `tenant_id + dept_id + product_id + create_time`，来源幂等查询索引包含 `tenant_id + dept_id + reference_type + reference_id + product_id`。

迁移必须幂等、非破坏、输出迁移前后重复键与异常数据对账结果。无法唯一推导租户的存量行不得默认归入当前租户并继续开放，应进入异常清单并阻断报表开放。

### 5.2 写入和锁定

所有库存写操作从可信登录上下文或已校验的业务单据取得租户和部门，不接受客户端指定租户。创建结存行、`SELECT ... FOR UPDATE`、读取已记录净额、写流水、更新结存必须使用相同的 `tenant_id + dept_id + product_id` 键并位于同一事务。

同一来源单据重试保持幂等；修改和删除采购/销售单通过目标净额差异写反向流水，不物理删除历史流水。所有 Mapper 更新必须检查影响行数。

### 5.3 快照

每日快照按租户、门店、商品重建，按升序确定锁定或读取顺序。快照日期 D 的口径为该自然日结束时结存：

- 期初：D 日第一笔流水前的数量，或 D-1 期末。
- 入库：D 日所有正向入库及销售冲销的分类汇总。
- 出库：D 日所有销售出库及采购冲销的分类汇总。
- 期末：期初加当日净变动。

历史补建必须从最早可信流水日按日顺序重放，不能用当前结存倒填所有历史日期。

## 6. 接口与权限

保留现有 `POST /finance/report/stock` 作为主查询接口，新增：

- `POST /finance/report/stock/summary`：完整结果汇总。
- `POST /finance/report/stock/page`：商品分页明细。
- `POST /finance/report/stock/ledger/page`：流水下钻。
- `POST /finance/report/stock/export`：导出。
- `POST /finance/report/stock/reconciliation`：只读对账结果，仅管理员或库存治理权限可访问。

如兼容性允许，主接口可组合返回 summary + page；服务端仍应将汇总查询和分页查询拆分为可独立测试的 Mapper 方法。

权限：

- 查看：`finance:report:stock`。
- 导出：`finance:report:stock:export`。
- 查看治理对账：`finance:stock:reconciliation`。

Controller 权限只是第一层；Service 必须重新取得当前租户和授权部门范围，校验日期、页大小、商品条件和状态枚举。

## 7. PC 交互

替换暂停页，页面由以下区域组成：

1. 查询栏：门店、日期、商品、状态。
2. 汇总卡片：期初、净入库、净出库、期末、负库存、低库存、滞销、异常。
3. 商品明细表：按门店 + 商品分页。
4. 流水抽屉：展示所选商品的区间流水和来源。
5. 口径说明：明确冲销归类、滞销阈值、数据更新时间和异常含义。

接口失败、授权范围为空、快照缺失或底座健康检查不通过时失败关闭，不展示零值假数据。服务端返回可解释原因，客户端原样展示安全的业务提示。

## 8. 第二期范围：财务库存计价

### 8.1 计价方法

采用移动加权平均法。采购净入库按实际采购单价进入成本池；每笔有效入库后：

`新平均成本 = (入库前库存金额 + 本次入库金额) / 入库后数量`

金额统一使用 `BigDecimal`、2 位小数和 `HALF_UP`。中间单位成本可保留 6 位，最终金额按 2 位固化；具体精度在数据库迁移和 Java 类型中保持一致。

### 8.2 成本流水

不能使用当前商品采购价回算历史销售成本。每笔销售出库必须固化当时单位成本和出库成本；销售冲销按原销售成本反向恢复。采购冲销必须关联原采购批次，并在不足以安全逆转成本层时拒绝自动冲销或生成明确调整任务。

第二期输出：期初库存金额、采购入库金额、销售成本、成本调整、期末库存金额、销售收入、毛利和毛利率。

### 8.3 会计期间

ACTIVE 期间允许在权限和并发规则下调整。LOCKED 或已结转期间不得回写历史成本流水和快照；差异在当前 ACTIVE 期间通过有原因、有操作者、有来源的成本调整流水处理。

## 9. 测试与验收

至少覆盖：

- 两个租户使用相同 `dept_id/product_id` 时互不影响。
- 未授权门店 ID 被拒绝或从查询范围剔除，且交集为空时失败关闭。
- 采购新增、修改、删除及重复请求的流水与结存一致。
- 进货单同商品普通数量与赠品数量共同入库，赠品金额为零但库存数量不为零。
- 销售新增时销售数量与赠品数量共同出库，赠品不增加销售收入。
- 修改进货/销售赠品数量、删除含赠品单据和重复请求的差额流水与结存一致。
- 销售修改、删除、库存不足和允许负库存配置。
- 采购冲销、销售冲销正确归入净入库/净出库。
- 跨日、无流水日、补建快照和历史缺口。
- 期初 + 净变动 = 期末，汇总与分页明细合计一致。
- 负库存、低库存、零库存、滞销、快照异常、流水异常分类。
- 导出与页面使用同一授权范围和查询口径。
- 第二期移动加权成本、销售成本固化、冲销、舍入和锁定期间。

## 10. 发布门禁

第一期报表菜单只有在以下条件全部满足后才能由暂停状态切换为开放：

1. 租户键迁移和唯一键调整已在目标环境验证。
2. 存量库存对账无未解释差异；允许存在的差异有明确异常清单和业务签字。
3. 快照补建完成且健康检查通过。
4. 后端权限、租户和授权部门测试通过。
5. PC 构建和真实 API 验收通过。
6. SQL 文本及非 ASCII 内容按 utf8mb4 验证。

第二期必须独立发布，不能以第一期上线为由提前展示未经验证的库存金额或毛利。

## 11. 执行 Agent 完成报告与复核

每个执行 Agent 完成一个任务后，必须生成任务完成报告，保存到：

`docs/superpowers/reports/2026-07-12-stock-report-task-<N>-completion.md`

报告必须包含：

- 任务编号和目标。
- 实际修改文件及其职责。
- 关键设计决定和与本规格的对应关系。
- GitNexus 修改前 impact 结果：直接调用者、受影响流程、风险等级；HIGH/CRITICAL 必须记录用户确认。
- 已执行的测试命令、结果和关键断言。
- 数据库迁移与对账输出；不涉及数据库时明确写“不涉及”。
- 权限、租户、部门、并发和财务边界的逐项自查。
- 已知限制、未完成项和后续风险；不得用“无”掩盖未验证内容。
- 提交 SHA，以及 `detect_changes(scope="staged")` 的预期影响范围。

执行 Agent 不得自行宣告整项功能完成。每份报告完成后交由主复核 Agent 复核。主复核 Agent 必须：

1. 对照本规格和开发计划检查范围与证据。
2. 独立查看代码差异和完成报告，不仅采信执行 Agent 结论。
3. 复跑聚焦测试，并按风险选择回归构建或真实 API 验证。
4. 检查 Critical/Important 审查项均已解决。
5. 检查暂存文件清单、`git diff --cached --check` 和 GitNexus `detect_changes`。
6. 输出 `APPROVED`、`CHANGES_REQUIRED` 或 `BLOCKED` 结论及理由。

只有主复核 Agent 给出 `APPROVED`，对应任务才可标记完成并进入下一发布门禁。
